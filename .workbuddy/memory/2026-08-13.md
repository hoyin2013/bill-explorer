## YOLOv8 小票检测 + 逐张 AI 识别（检测增强）
需求：models/ticket_detect.pt 是自己训练的 YOLOv8 小票检测模型，可框出每张小票边界。在此基础上有针对性地逐张裁剪、再用 AI 识别每张的人名与内容，提高识别率；同时在前端预览上用矩形框标出边界。

### 架构
主进程 spawn Python（ultralytics 加载模型）检测 → 返回每张票的框（预览缩放图像素坐标）+ 裁剪 base64 → 主进程对每张裁剪图调用视觉 AI（带人名清单、人名修正）→ 合并结果。检测输入用 `readImageBase64` 的缩放后 JPEG（maxWidth 1600），故框坐标天然对齐预览、裁剪图直接喂 AI。模型/Python 不可用时自动回退整图识别，不崩溃。

## 【重大 Bug 修复】ONNX 检测效果远差于原 Python/ultralytics（"差距巨大"根因）
用户反馈切到 ONNX 后检测效果与原 Python/ultralytics 差距巨大。用 pic/1.jpg 做 A/B 对照（同图、同 conf=0.25），用本机 `/usr/local/bin/python3.14`（已装 ultralytics 8.4.118 + torch 2.13.0）跑原脚本对比：
- 原 Python/ultralytics：22 框，conf 0.315–0.908，坐标合理（x≈600–4036，每张约 1100×750）。
- ONNX（修复前）：70 框但**所有 conf=1.000**、坐标塌缩成 x=0,y=0 的碎片框。
### 根因（两处，都在 `scripts/detect_onnx.mjs`）
1. **输出张量布局解析两分支写反**：ONNX 输出 dims=[1,5,8400]（通道 C=5 在中维、锚点 A=8400 在末维）。`valAt` 写成 `layout==='CA'? data[a*C+c] : data[c*A+a]`，两个分支恰好对调 → 把"类分数"读成了框坐标，sigmoid 后恒为 1.0，阈值失效、碎片框全漏入。修正：`chanDimIs1 = dims[1]===C`，`valAt=(a,c)=> chanDimIs1? data[c*A+a] : data[a*C+c]`。
2. **类分数被多算了一次 sigmoid（double-sigmoid）**：导出图里类分数**已含 sigmoid**（通道 4 原始值域 0.00–0.97，是概率）。但原 `needSigmoid` 判断扫描了**整个张量**（含框坐标 0–664），误判"需要 sigmoid"，于是对已是概率的类分数再 sigmoid → sigmoid(0.97)=0.725，等同废掉 0.25 阈值、8400 锚点全过 → 934 框。修正：`needSigmoid` **只扫描类通道自身值域**（c from 4 to C-1），类分数已落在 [0,1] 则不再 sigmoid。
### 验证（关键对照，证明不是模型问题）
- `yolo predict model=models/ticket_detect.onnx`（ultralytics 原生 ONNX 推理，同一前后处理）：conf=0.25 给 **20 框、conf 0.288–0.974** → 证明 ONNX 模型本身没问题，差距纯属 mjs 后处理 bug。
- 修复后 ONNX 路径对 pic/1.jpg：20 框、conf **0.303–0.975**，坐标与 Python 高度吻合（如 PY#0 3918,46,1157×743 / ONNX#0 3916,31,1160×767），21/22 个 Python 框被匹配。
- 完整（含裁剪）端到端：20 框 / 20 裁剪图，box 含 x,y,w,h,conf,cls,label,angle，crop 为合法 base64 JPEG。
- 诊断中曾把 `models/ticket_detect.onnx` 重导出为不带 simplify（验证 simplify 不是元凶）；最终**恢复为与用户原始一致的 simplify=True** 导出，确认两次导出检测结果一致。
### 经验
- YOLOv8 ONNX 输出布局：通道在中维/末维都要正确处理；**类分数是否需 sigmoid 要看该通道自身值域（落在 [0,1] 说明已 sigmoid），绝不能扫描整张张量**——框坐标 0~640 会污染判断。
- 怀疑 ONNX 不如 torch 时，先用 `yolo predict model=xxx.onnx` 跑同一模型做"黄金对照"，能立刻区分是模型导出问题还是自家后处理问题。

### ⚠️ 开发模式关键坑：Electron 主进程不热更新
- 本应用 dev 启动（`run-dev.sh` 或 `npm run build && npx electron .`）：渲染进程由 Vite dev server 提供，改 `src/renderer/**` 会**热更新**即时生效；但主进程（`src/main/**`）打包进 `dist-electron/main.js` 后由 Electron **一次性加载进内存，不会热更新**。
- 现象：改了 `main.ts`（如本次"关窗清空搜索框"的 `image-window-closed` 发送逻辑）并 `npm run build:main` 后，磁盘文件已含修复，但**仍在运行的那条 Electron 进程跑的是旧内存代码**，新逻辑不触发，表现为"改了没生效"。
- 排查方法：`pgrep -fl "Electron.app/Contents/MacOS/Electron"` 看是否有旧进程；`grep -c "image-window-closed" dist-electron/main.js` 确认磁盘构建含修复。
- 解决：**改完 `main.ts` 后必须让用户完全退出并重启整个 App（Cmd+Q 应用，不是只关子窗口）**，主进程才会重新加载新 `dist-electron/main.js`。或开发期用 `npm run electron:watch` 让主进程随文件改动自动重建（但 Electron 仍需手动重启一次才会 reload 新进程二进制）。
- 推论：若用户反馈"某 main.ts 改动不生效"，优先怀疑是旧主进程没重启，而非代码错误（除非 `grep` 显示磁盘构建里也没有该改动）。

## 修复：关 AI 窗口不清空搜索框 + 关主窗口 AI 窗口不跟着关（2026-08-13 晚）
用户用 `npm run electron:preview`（`npm run build && electron .`）复现：①关 AI 识图窗口，主窗口搜索框没清空；②关主窗口，AI 窗口没一起关。
### 根因（真 bug，非旧进程）
1. `mainWindow` 关闭后**没有置空**，变成"已销毁但非 null"的对象。`imageWindow.on('closed')` 里 `mainWindow?.webContents.send(...)` 访问已销毁的 webContents **抛错**，导致第二行 `send('image-window-closed')` 被跳过 → 搜索框清不掉（用户先关了主窗口再关 AI 窗口时必现）。
2. macOS 的 `app.on('window-all-closed')` 原逻辑 `if (process.platform!=='darwin') app.quit()` 在 darwin 上**不退出**，所以关主窗口后 AI 窗口还赖着、应用也不退。
### 改动（`src/main/main.ts`）
- `createWindow()` 内新增 `mainWindow.on('closed', () => { if (imageWindow && !imageWindow.isDestroyed()) imageWindow.destroy() })` —— 关主窗口即销毁 AI 窗口。
- `imageWindow.on('closed')` 发送前先 `if (mainWindow && !mainWindow.isDestroyed())` 判断并包 `try/catch`，避免销毁态 webContents 抛错吞掉 `image-window-closed` 发送。
- `window-all-closed` 改为**总是 `app.quit()`**（关主窗口→AI 销毁→全关→整体退出，不再按平台保留后台）。
### 验证
- `npm run build:main` 通过；`dist-electron/main.js` 含 `image-window-closed`(1)、`isDestroyed()`(3)、`app.quit()`(1)、`imageWindow.destroy`(1)。
- `electron:preview` 会先全量 `npm run build`，故重跑即生效。
