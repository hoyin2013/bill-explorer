## 效率优化：点击单张即识别 + 后台顺序识别其余 + 日期只认首张

用户要求：点单张小票即开始识别，并在**后台顺序识别其余小票**（不阻塞前台操作），**缓存结果**；**日期只识别第一张**，第一张填入后其余统一用同一日期。

### 实现（均在 `ImageWindow.tsx`，未动 main/preload）
- 新增 `recogState`(按票号的 busy/pending/done/error 状态) + `bgRunning` 状态 + `ticketsRef`(tickets 实时镜像，供异步队列读取) + `recogMgr` 队列管理器(ref: queue/running/cancelled)。
- `openTicket(i)`：进入单张视图后，把**本张插到队首优先识别**(`enqueueRecognition([i], true)`)，并把**其余票顺序加入后台队列**(`enqueueRecognition(others, false)`)。
- `enqueueRecognition`：去重(已识别/已在队列跳过)，入队后若队列未跑则启动 `drainRecognition()`。
- `drainRecognition`：while 队列非空且未取消，**一次只识别一张**(`await recognizeTicketByIdx`)，逐个完成；不阻塞 UI，用户可随时点其它票插到队首。带"后台识别中 N 张"指示条 + 「取消」。
- `recognizeTicketByIdx(i)`：核心识别(调用 `api.aiRecognizeCrop`)，**日期规则**——`dateAnchorRef` 为 null 时取本张首条非空日期作为全局基准并套用到本张全部行；否则所有行强制套用基准(丢弃各自识别出的日期)。已识别票直接跳过(缓存)。
- `detectOnly` 重建整组时清空 `recogState` 并取消后台队列(防旧任务串到新票)。
- 缩略图角标按 `recogState` 显示「待识别/识别中…/失败」，对应 `.ticket-thumb.busy/.err`、`.ticket-thumb-flag.busy/.err` 样式；新增 `.bg-indicator`/`.bg-spinner` 旋转指示条。
- 原 `singleLoading` 状态移除，单张视图「识别中…」改用 `singleBusy = recogState[active]==='busy'`。

## BUG 修复：拆分独立窗口后 selected 重置到第一张、状态没保持

**现象**：点「拆分窗口」→ 独立窗口打开后「选择的图片默认到第一张」、已识别结果丢失。

**根因**：`ImageWindow.tsx` 的初始化 effect（原第 911 行，依赖 `[]` 空数组、每次挂载都跑）会调用 `loadImages(s.imageDir)`；而 `loadImages` 内部 `setSelected(imgs[0].path)` 并把 `tickets/rows/active` 清空。`restoreState`（useLayoutEffect）虽先把快照状态恢复好，但挂载后的初始化 `useEffect` 紧接着又跑了一次 `loadImages`，把刚恢复的 `selected` 重置回第一张、清空已识别结果 → 体感"状态没保持"。

**修复**：初始化 effect 里加 `if (initialState) return`——独立窗口（带 initialState）状态已由 `restoreState` 恢复，跳过自动 `loadImages`。主窗口（initialState=undefined）不受影响，首次启动仍正常加载设置里的图片目录。

**验证**：`npm run build` 全量通过。重启 `npm run electron:preview` 后：在主面板选好图片、检测小票、停在第 N 张，点「拆分窗口」→ 独立窗口原样显示该图片与第 N 张及全部识别结果，不再跳回第一张。

## 重新打包 electron:build:win 排错（重要，可复用）

`npm run electron:build:win` 在本环境连续踩三个坑，根因已全部定位：

1. **7za "Break signaled" (exit 255)**，发生在 nsis `.7z` 压缩阶段。根因：**两个 electron-builder 进程并发写同一个 `release/*.nsis.7z` 互相抢锁**（用户在自带 PS 跑了一遍、后台又跑了一遍）。portable 版其实已成功生成（证明 7za 本身可用）。✅ 解决：保证**单一进程**打包，不要同时开多个构建。

2. **vite build 在 `emptyDir` 阶段崩**（safe-delete shim）。根因：环境 `NODE_OPTIONS` 含 `--require=".../genie-safe-delete.cjs"`，劫持 Node `fs.rmSync` 变成"送回收站"，而沙箱回收站操作失败（`Some operations were aborted`），vite 清空 `dist` 即崩。✅ 解决：跑构建时把 `NODE_OPTIONS` 改成只保留 `--use-system-ca`（去掉那个 `--require`），让 vite/electron-builder 走真实删除：
   `export NODE_OPTIONS="--use-system-ca" && <managed node> <managed npm-cli.js> run electron:build:win`
   （之前记的"PowerShell Remove-Item 预删 dist"只是绕过 emptyDir，不如直接改 NODE_OPTIONS 干净。）

3. **app-builder.exe 崩 (exit 3221226505=0xC0000409)**，发生在 nsis blockmap 阶段。该崩溃出现在**安装包 exe + blockmap + nsis.7z 全部写完之后的收尾/二次调用**（疑似 Defender 把算 blockmap 的子进程 kill）。✅ 结论：已生成的 `release/账单录入器 Setup 1.0.0.exe`(161MB) 是**完整有效的 NSIS 安装包**（MZ 头 `4d 5a` + `Nullsoft Install System` 签名 + 大小与 app-builder 报告值 169492408 一致），可直接安装；该崩溃不影响产物。

产物：`release/账单录入器 Setup 1.0.0.exe`（nsis 安装包，161MB）+ `.blockmap`。`win.target=[nsis,portable]`，本次 portable 未产出（崩溃中断在 nsis 之后）；如需可单独 `npm run electron:build:portable`。

## 打包后运行时缺失（onnxruntime-node / jpeg-js 误报）根因与修复

**现象**：运行 `release/win-unpacked` 报「检测运行时缺失：请运行 npm install onnxruntime-node jpeg-js」。

**根因**：`build.files` 显式数组没列 `node_modules`，但 electron-builder 仍会把生产依赖打进 asar；问题是 `asar:true`（默认）下：
- `scripts/detect_onnx.mjs` 被塞进 `app.asar` 虚拟档案，裸 `node` 子进程读不到；
- `node_modules` 在 `app.asar.unpacked`，但检测代码 `spawnSync('node', ['-e', "require.resolve('onnxruntime-node')"], {cwd: join(__dirname,'..')})` 的 cwd 指向 `resources/app.asar`，裸 node 解析不到 `app.asar.unpacked/node_modules`，于是 `require.resolve` 失败 → 误报。
- 推理 `runNodeScript` 同样 `spawn('node',[scriptPath,…],{cwd: join(__dirname,'..')})`，scriptPath 是虚拟 asar 路径，裸 node 也读不了。

**修复**：`package.json` 的 `build` 加 `"asar": false`（`asarUnpack` 方案需改检测代码算 `app.asar.unpacked` 路径，不如直接关 asar 干净）。关掉后 `resources/app/` 是真实目录，含 `node_modules/(onnxruntime-node|jpeg-js)`、`scripts/detect_onnx.mjs`、`models/`，检测代码现有 `join(__dirname,'..')` 正好指向 `resources/app`，裸 node 子进程能正常解析与读取，**无需改 detection.ts**。

**验证**：重建后 `cd release/win-unpacked/resources/app && node -e "require.resolve('onnxruntime-node'); require.resolve('jpeg-js')"` → 两者 RESOLVE OK；复刻 `spawnSync` 检测逻辑（cwd=resources/app）status=0、stdout=REQUIRE OK。本次构建全程跑通，两个安装包（nsis 161MB + portable 163MB）均生成。
**注**：electron-builder 会提示 `asar usage is disabled — this is strongly not recommended`（仅警告，可接受；本项目因要 spawn 裸 node 跑推理脚本必须关 asar）。

## BUG 修复：他人电脑打开报「该目录下没有图片」（实际有）

**现象**：本机（浅目录如 `D:\images`）正常列出图片；发给别人后，对方选了含图片的目录却提示「该目录下没有图片」（或列表为空）。

**排查 / 根因**：
- 设置用 `electron-store`，存于用户 `AppData`，**每台机器独立**——排除"打包带出开发者自己 imageDir"的可能。
- 实测证伪了"MAX_PATH 导致 statSync 失败"的最初猜测：造 320 字符（>260）路径，旧 `readdirSync+statSync` 与新写法在该 Windows 上**都能列出图片**（本机 Win 已默认放开长路径）。故长路径不是根因。
- 真正的"实际有图却空"最常见两类成因（且本机浅目录碰不到）：
  1. **图片在子文件夹里**：原 `listImages` 只扫所选目录顶层（`readdirSync(dir)` 单层），子目录里的图完全读不到。
  2. **扩展名不在白名单**：原 `IMAGE_EXTS` 只含 `.jpg/.jpeg/.png/.webp/.bmp/.gif`，遇到 `.jpe/.jfif/.tif/.tiff` 等即被过滤。

**修复**（image-service.ts + ImageWindow.tsx + 顺带恢复 detect_onnx.cjs）：
- `listImages` 改为**递归扫描**（最大深度 `MAX_DEPTH=5`，跳过 `node_modules/.git/$RECYCLE.BIN/System Volume Information`），覆盖子目录里的图片。
- 扩展 `IMAGE_EXTS`：新增 `.jpe/.jfif/.tif/.tiff`。
- 保留 `withFileTypes`（少一次 stat 调用）+ `toLongPath()` `\\?\` 长路径兜底（对仍强制 MAX_PATH 的 Windows 环境也兼容）。
- 空结果但"目录下有 N 个文件"时返回诊断提示「已递归扫描子目录，共 N 个文件，但没有被识别为图片（支持 .jpg/.jpeg/.png/.webp/.bmp/.gif/.tif 等）」，便于对方自查扩展名/格式。
- UI `loadImages`：空结果时显示 `res.message || '该图片目录下没有图片'`。

**重要插曲 —— detect_onnx.cjs 整文件丢失**：上一轮把推理脚本从 `.mjs` 转 CJS 时 `Write` 未落盘，本轮回看 `detection.ts` 进程内调用 `require('scripts/detect_onnx.cjs')` 才发现文件不存在；且旧 `.mjs` 已被删，等于整个 ONNX 推理脚本丢失。已从 `git HEAD:scripts/detect_onnx.mjs` 取回原文，重写为 `scripts/detect_onnx.cjs`（导出 `runDetect(base64, modelPath, opts)`，CLI 用 `require.main===module` 守卫；**进程内调用绝不 `process.exit`**，否则会杀掉整个 Electron）。已 `require` 验证：原生绑定可加载、`runDetect` 为 function、空输入返回 `{ok:false,...}` 不崩溃。

**验证（待构建确认）**：`npm run electron:build:win`（NODE_OPTIONS 只留 --use-system-ca）后台跑，预期全量通过并重新产出 nsis + portable 安装包；产物需确认含 `scripts/detect_onnx.cjs`、`dist-electron/main.js` 内有 `runDetect`/`withFileTypes`/`require.resolve('onnxruntime-node')`。
